# CRITERIA — 평가 기준·레벨·보고서 목차·검수 기준

계획서 4장(평가 관점 및 기준), 5장 일부, 6장(보고서 목차)을 코드 작성용으로 옮긴 문서.
프롬프트는 이 문서의 "평가 질문"과 "판정 방식"을 그대로 인용한다. `details` 키는 `docs/CONTRACTS.md` §2 표와 동일하다.

## 0. 평가의 성격

- 기술의 우열이나 추천 순위를 산출하지 않는다. 동일한 KV cache 병목이 관점·조건에 따라 어떻게 다르게 평가되는지 조사한다.
- 관점별 레벨은 합산·평균하지 않는다. 차이는 "현재 공개 근거로 확인되는 단계의 차이"로만 서술한다.
- 두 기술(`mla`, `pim_cxl`)에 동일한 15개 기준을 적용한다. 결과 = 30개 `CriterionResult`.

## 1. 공통 판정 원칙

| 원칙 | 내용 |
|---|---|
| 평가 단위 | TRL과 기술 개요는 선정 논문·구현 단위(`unit="paper"`). 시장성과 이해관계자는 MLA 계열 / CXL·PIM/PNM 계열 단위(`unit="family"`)로 확장. 결과에 어느 단위 근거인지 표시. 확장 사실은 보고서 한계점에 명시 |
| 근거 | 기준마다 원문 인용과 출처 위치를 연결. 못 찾은 정보는 추측하지 않고 `not_public`으로 기록하며 검색어·검색일·확인 범위를 남김 |
| 신뢰도 | `high`: 독립 출처 2개 이상이며 논문/공식 자료 포함. `medium`: 출처 하나 또는 2차 자료만. `low`: 추론(inference) 또는 비공개 항목 포함 |
| 중립성 | 관점별 레벨 합산·순위 금지. TRL 차이를 우열로 해석하지 않음 |
| 수치 비교 | 서로 다른 실험 값을 그대로 비교하지 않음. 모델 규모·컨텍스트·하드웨어·베이스라인을 함께 기록 |

## 2. 관점별 평가 기준 (15개)

### 2.1 기술 성숙도 (TRL) — 개별 기술 단위 — 담당 B (`run_tech_research`)

| ID | 평가 질문 | 판정 방식 | `level` 값 |
|---|---|---|---|
| **T1 현재 TRL** | 공개 근거로 확인 가능한 가장 높은 단계는 어디인가? | TRL 1-3 / 4-6 / 7-9 구간 + 구간 내 추정치. "공개 정보 기반 추정" 표기, 인용 근거, **한 단계 위로 올리지 못한 이유** 필수 기재 | `"TRL 1-3"` / `"TRL 4-6"` / `"TRL 7-9"`, `level_estimate`에 추정치 |
| **T2 검증 환경** | 해석·시뮬레이션·실물 시제품·실서비스 중 어디에서 검증됐는가? | L1 해석·수식 / L2 시뮬레이션 / L3 실물 HW 시제품 / L4 실서비스 트래픽 | `"L1"`~`"L4"` |
| **T3 재현성** | 코드, 모델/설계, 평가 스크립트·데이터, 제3자 재현이 공개됐는가? | 4개 확인 항목 기준 L3(3~4개) / L2(1~2개) / L1(0개, 원저자 자료만) / L0 미확인 | `"L0"`~`"L3"` |
| **T4 다음 과제** | 상위 TRL로 이동하려면 무엇이 남았고 무엇이 공개되지 않았는가? | 서술형. `remaining_tasks`와 `not_public_items`를 분리 | `"narrative"` |

TRL 참고 구간: 1-3 기초 원리·개념·실험적 검증(해석/시뮬레이션), 4-6 실험실~관련 환경에서 구성요소/시스템 검증(시제품), 7-9 실제 운용 환경 시연~실서비스 운영.

### 2.2 시장성 — 기술 계열 단위 — 담당 C (`run_market_eval`)

| ID | 평가 질문 | 판정 방식 | `level` 값 |
|---|---|---|---|
| **M1 성장성** | 수요 동인과 정량 시장 전망이 독립 출처에서 확인되는가? | L3 확산 / L2 형성 / L1 태동 / L0 미확인. 시장 수치에 **발행 주체·시점 병기**, 단일 전망을 사실로 단정하지 않음 | `"L0"`~`"L3"` |
| **M2 채택** | 연구·PoC·제품화·상용 운영 중 어느 단계의 사례가 확인되는가? | L4 상용 운영 / L3 제품화 / L2 시범·PoC / L1 연구 / L0 미확인. **채택 주체 필수** | `"L0"`~`"L4"` |
| **M3 생태계** | 프레임워크, 벤더 제품, 표준화, 제3자 연구·도구가 존재하는가? | 4개 항목 Y/N과 근거 제시 → L3(3~4) / L2(1~2) / L1(0, 원저자만) / L0 | `"L0"`~`"L3"` |

### 2.3 이해관계자 — 4주체 고정 — 담당 C (`run_stakeholder_eval`)

4주체: 모델 개발사(`model_developer`) / 클라우드·서빙 운영사(`cloud_serving_operator`) / 메모리·반도체 벤더(`memory_semiconductor_vendor`) / 투자 업계(`investor`)

| ID | 평가 질문 | 판정 방식 | `level` 값 |
|---|---|---|---|
| **S1 의사결정** | 각 주체는 어떤 역할인가? | 각 주체를 결정권자/영향받는 자/공급자/무관으로 명시하고 근거 연결 | `"assigned"` (판정은 `details.roles`) |
| **S2 편익** | 각 주체가 얻는 기술적·경제적 편익은? | 4주체 각각 최소 1개. 직접 자료가 없으면 근거 ID를 단 `inference`로 표시 | `"narrative"` |
| **S3 부담** | 도입 비용, 전환 부담, 기존 사업과의 충돌은? | 4주체 각각 최소 1개. S2와 동일한 증거 규칙 | `"narrative"` |
| **S4 상충** | 한 주체의 편익이 다른 주체의 부담이 되는 지점은? | 기술별 최소 1쌍. "A에게 편익인 것이 B에게 부담" 형식. **종합 단계의 핵심 입력** | `"narrative"` |

### 2.4 도메인 적합성 — 대규모 데이터센터 장문맥 추론 — 담당 B (`run_domain_eval`)

| ID | 평가 질문 | 판정 방식 | `level` 값 |
|---|---|---|---|
| **D1 장문맥 병목** | KV cache 부담이 얼마나 감소하거나 어느 계층으로 이전되는가? | 수치 크기에 등급을 매기지 않고, 우리 도메인 조건과의 **직접성**을 L3 직접 근거 / L2 간접 근거(외삽 논리 필수) / L1 근거 없음으로 판정 | `"L1"`~`"L3"` |
| **D2 동시 처리** | 배치 크기·동시 세션·생성 처리량에 어떤 영향을 주는가? | D1과 동일 | `"L1"`~`"L3"` |
| **D3 지연·에너지·비용** | TTFT/TPOT, 토큰당 에너지, 전송 오버헤드, 총비용 근거가 있는가? | D1과 동일 | `"L1"`~`"L3"` |
| **D4 변경 범위** | 모델 재학습·변환, 서빙 엔진 수정, HW 교체, 메모리 추가가 필요한가? | 6개 체크 항목을 Y / N / 미확인으로 기록. **예상 답을 프롬프트에 미리 주입하지 않음** | `"checklist"` |

D1~D3의 모든 수치는 `Measurement`(모델 규모·컨텍스트·하드웨어·베이스라인·배치)와 함께 저장한다. L2/L3 판정에는 Measurement가 최소 1개 있어야 하고, L1(근거 없음)은 수치 없이 "찾아봤으나 도메인 조건에 대한 수치 근거가 없다"는 판정이다(근거 자체를 못 찾은 `not_public`과 구분).

## 3. 관점 노드 출력 계약 (계획서 4.3)

각 결과에는 기준 ID, 판정 레벨, 2~4문장의 평가 내용, 인용 근거와 출처 위치, 신뢰도를 포함한다. Pydantic 검증을 통과하지 못한 결과(기준·근거 누락)는 종합 단계로 넘기지 않는다. → `CriterionResult` (CONTRACTS.md §2)

## 4. Graph 제어 규칙 (계획서 5.2)

| 지점 | 규칙 | 상한 |
|---|---|---|
| 기술 조사 재검색 | 기술 원리·한계·수치·측정 조건이 빠지면 검색어를 바꿔 다시 찾음. 그래도 없으면 `not_public` | 2회 |
| 관점별 평가 | 기술 조사 완료 후 시장·이해관계자·도메인 **동시** 시작. 각 결과는 별도 State 키 | — |
| 누락 항목 재실행 | T1~T4 누락 → 기술 조사로 복귀. M·S·D 누락 → 해당 기준을 맡은 에이전트만 재실행 | 기준별 2회 |
| 반대 근거 | 한쪽 기술 근거만 많거나 반대 근거가 없으면 한 번 더 검색 | 1회 |
| 보고서 검수 | 근거·기준 반영 확인, 문제 시 수정 | 1회 재생성 |

## 5. 보고서 목차 (계획서 6장) — 담당 D (`run_report`)

| 챕터 | 분량 | 내용 |
|---|---|---|
| **SUMMARY** | ≤ 1/2 p | 두 기술이 관점별로 다르게 평가되는 지점의 핵심 결론 3~4문장 |
| **1. 분석 배경** | 0.5~1 p | KV cache가 메모리 병목이 되는 구조, SW/HW 두 접근의 분기, 대규모 데이터센터 장문맥 추론 환경을 대상으로 삼은 이유 |
| **2. 기술 선정** | 0.5 p | MLA / PIM·CXL 선정, 선정 기준(대표성·대조성·자료 확보 가능성)과 후보 검토 결과(TurboQuant·KIVI 등, `kv_survey` 참고) |
| **3. 기술 개요** | 1~1.5 p | 각 기술의 핵심 접근, 정량 성과, 명시된 한계 (원문 근거 인용) — `tech_profiles` |
| **4. 관점별 평가** | 3~4 p | 4.1 TRL / 4.2 시장성 / 4.3 이해관계자 / 4.4 도메인 적합성. **각 절 말미에 기술 × 기준 요약표** |
| **5. 시사점** | 1~1.5 p | 관점 간 상충 지점 중심. 우열이 아닌 **기준 차이**로 원인 서술 — `synthesis.conflicts` |
| **6. 한계점** | 0.5 p | 공개 정보만으로 TRL 추정한 한계 / 시장·이해관계자를 기술 계열 단위로 확장한 사실 / 제안사 발표 자료 의존 비율(`evidence_gap.vendor_source_ratio`) / 편향 축소를 위해 적용한 검사와 남은 한계 |
| **REFERENCE** | — | 실제 인용한 자료만. `Evidence.source_type`별 자동 포맷 |

REFERENCE 형식 (`format_reference`):
- 논문: `저자(YYYY). 제목. 학술지/arXiv, 권(호), 페이지.`
- 특허: `출원인(YYYY-MM). 특허명, 번호, URL`
- 웹: `기관(YYYY-MM-DD). 제목. 사이트명, URL`
- 본문 인용 표기: `[E: mla-T1-01]` 형태의 evidence_id 각주. REFERENCE는 본문에 등장한 evidence_id만 나열한다.

## 6. 보고서 검수 기준 (계획서 4.4) — 담당 E (`control/judge.py`)

기술 평가 기준과 보고서 검수 기준은 분리한다. 생성 모델(`LLM_MODEL`)과 검수 모델(`JUDGE_MODEL`)은 다르다. **분량·마크다운 장식 자체는 채점하지 않는다.**

| 차원 | 1점 | 3점 | 5점 |
|---|---|---|---|
| **근거성 (evidence)** | 근거 없는 판정 문장이 있거나 REFERENCE에 본문 미인용 항목이 있음 | 모든 판정에 근거가 있으나 일부 인용 위치가 불명확 | 모든 판정이 evidence_id로 연결되고 위치·출처가 명확 |
| **기준 준수 (criteria_compliance)** | 15기준 × 2기술 중 누락이 있거나 레벨 체계를 벗어남 | 모두 존재하나 판정 방식(예: T1 '올리지 못한 이유', D2 외삽 논리) 일부 미기재 | 모든 기준이 CRITERIA.md 판정 방식대로 기재 |
| **중립성 (neutrality)** | 우열·추천·순위·합산 점수 표현 존재 | 우열 표현은 없으나 한쪽 기술에 근거 비대칭이 있음에도 언급 없음 | 차이를 기준·단위·근거 유형 차이로만 서술하고 비대칭을 한계점에 명시 |
| **구체성 (specificity)** | 수치가 조건 없이 등장하거나 추상적 서술만 있음 | 수치에 조건이 있으나 일부 누락 | 모든 수치에 모델 규모·컨텍스트·HW·베이스라인 병기, 상충 지점이 구체적 |
| **형식 (format)** | 필수 챕터 누락 또는 요약표 없음 | 챕터는 모두 있으나 요약표·REFERENCE 형식 일부 불일치 | 목차·요약표·REFERENCE 형식 모두 준수 |

판정: 하나라도 1점이거나 `missing_required`가 비어 있지 않으면 `passed=False` → 1회 재생성(`revision_instructions`를 `ReportInput.judge_result`로 전달). 재생성 후에는 결과와 무관하게 PDF 출력으로 진행하되 `judge_result`를 실행 로그에 남긴다.

## 7. 코퍼스

| doc_id | 논문 | 종류 | 역할 |
|---|---|---|---|
| `deepseek_v2` | DeepSeek-V2 (2024-06) | 원문 | `mla` 선정 논문. T·D 기준의 1차 근거 |
| `pim_cxl_1m` | 1M-Token LLM Inference — PIM/CXL (2025-10) | 원문 | `pim_cxl` 선정 논문. T·D 기준의 1차 근거 |
| `io_survey` | I/O for LLM inference: a survey of storage and memory bottlenecks (2026-07) | 서베이 | 메모리·스토리지 병목 배경(보고서 1장), HW 계층 확장 계열 맥락, 반대 근거 |
| `kv_survey` | A Survey on Large Language Model Acceleration based on KV Cache Management (Li et al.) | 서베이 | KV cache 관리 기법 분류·비교(보고서 2장 후보 검토), SW 축소 계열 맥락, 반대 근거 |

서베이 활용 규칙:
- 선정 기술의 T1~T4·D1~D4 판정 근거는 **원문 2편**에서 가져온다. 서베이가 선정 논문을 인용·요약한 내용은 2차 자료(`medium` 이하)로 취급한다.
- 서베이는 `unit="family"` 근거(기술 계열 맥락), 비교 후보 검토, 반대 근거 탐색, 보고서 1·2·6장 배경 서술에 쓴다.
- 서베이의 수치를 인용할 때는 서베이가 인용한 원 출처를 `condition_note`에 병기한다.

기술 선정 사유(보고서 2장에 사용):
- MLA: 대표성(어텐션 구조 재설계로 KV를 저차원 잠재공간에 압축, 논문 보고 KV cache 93.3% 감소) / 대조성(기존 GPU·HBM 인프라에서 운용 가능하나 모델 구조와 서빙 최적화 필요) / 자료 확보(공개 모델·논문·서빙 프레임워크). TurboQuant·KIVI 등 비교 후보는 `kv_survey`의 분류를 참고해 검토.
- PIM/CXL: 대표성(KV cache를 CXL 메모리로 확장하고 토큰 페이지 선택 연산을 메모리 측 가속기로 이관) / 대조성(서버 HW·메모리 계층·서빙 경로 변경 전제) / 자료 확보(논문 실험 + CXL·PIM/PNM 벤더 발표·표준화·후속 연구). **논문 시제품과 기술 계열 전체의 상용화 근거를 구분해 기록.**
